# 方向探讨：从「出海建站模拟器」到「人生模拟平台」

> 背景：在《出海建站模拟器》需求拆解（见 `site-builder-tycoon/需求拆解与可行性分析.md`）之后，
> 提出了更大的想法——做类似《模拟人生》的游戏：体验不同人生、经历不同事件、
> 通过选择延伸出多种开放性结局。本文用主流游戏设计框架分析两个方向的关系与取舍。

---

## 1. 先厘清一个关键概念：「模拟人生」其实是两种完全不同的游戏

「体验不同人生」这个愿望，在游戏史上有两条截然不同的实现路径，**规模差 10~100 倍**：

| | A. 系统涌现式沙盒（The Sims 本尊） | B. 事件驱动式人生模拟（BitLife / 人生重开 / 中国式家长 / Reigns） |
|---|---|---|
| 核心机制 | 模拟角色的需求、AI 自主行为、物理空间，故事从系统中**涌现** | 作者编写事件卡池，按角色状态抽取，故事由**内容 + 选择**组成 |
| 内容来源 | 系统交互（编程复杂度极高） | 文案创作（写作量大但可控） |
| 团队规模 | EA 级，百人团队多年 | 1~5 人可做，且已有多个爆款先例 |
| 结局开放性 | 完全开放（没有"结局"概念） | 通过状态驱动结局实现"伪开放"（足够好） |
| 对我们的可行性 | ❌ 不可行，别碰 | ✅ 完全可行 |

**结论：我们说的"模拟人生"，实际应该做的是 B。** 而且一个重要发现：
**《出海建站模拟器》本身就是一个 B 类游戏——只是把"人生"垂直到了"出海建站"这一种。**

两个想法不是二选一，是同一棵技术树上的两个节点。

## 2. 统一架构：「人生引擎」+「人生包」

正确的做法不是先做小游戏、以后推倒重做大的，而是**一开始就把引擎和内容分离**：

```
┌─────────────────────────────────────────────┐
│  人生引擎（通用，代码层）                      │
│  角色属性系统 / storylet 事件引擎 / 条件与权重  │
│  抽卡调度 / 状态驱动结局评价器 / 结局卡生成      │
├─────────────────────────────────────────────┤
│  人生包（内容层，纯 JSON/文案）                 │
│  📦 出海建站人生（第一个包，垂直验证）           │
│  📦 摆摊人生 / 考研考公人生 / 留学人生 / ...     │
│  📦 社区投稿人生包（远期 UGC）                  │
└─────────────────────────────────────────────┘
```

这正好呼应仓库名 **FableUnion——不同人生故事（Fable）的联合体（Union）**。
产品愿景可以升维成："每个人生包是一面镜子，玩家在别人的人生里认出自己。"

**但发布顺序必须是垂直优先**：先用《出海建站》一个包验证引擎 + 内容生产管线 + 传播模型。
直接做"大而全的人生模拟"会死于内容摊薄——每种人生都浅尝辄止，哪个人群都不共鸣。
垂直包的受众锋利度（出海圈自来水传播）是冷启动的命根子。

## 3. 主流游戏设计框架下，应该怎么做

### 3.1 MDA 框架：先定体验（Aesthetics），再倒推机制

目标美学排序：**叙事（Narrative）> 发现（Discovery）> 表达（Expression）> 挑战（Challenge）**。
即：共鸣的故事第一，"居然还有这种事件/结局"的探索感第二，"这局活成了我想要的样子"第三，数值挑战最后。
一切机制取舍用这个排序裁决——例如数值平衡做到"不出戏"即可，不必做到竞技级。

### 3.2 分支叙事的工程化：用 Storylet，不用剧情树

「很多选项延伸出多种结果」如果用显式分支树实现，内容量指数爆炸（10 个二选一 = 1024 条路径），
这是所有新手团队做开放叙事的死亡陷阱。业界成熟解法（Fallen London、80 Days、Reigns、King of Dragon Pass）：

1. **Storylet（故事单元）**：每个事件是独立单元，带 `前置条件 + 权重 + 后果（改状态）`。
   事件之间不直接相连，通过**状态**间接耦合。加内容 = 加卡片，成本线性而非指数。
2. **Quality-Based Narrative（状态驱动叙事）**：玩家的"故事线"不是预写的路径，
   而是属性/标签/旗标（flags）的轨迹。"和家人决裂"不是一个分支，而是一个 `家庭关系<0` 的状态，
   后续几十张卡都会因它改变文案和选项——玩家感知到的就是"我的选择改变了人生"。
3. **Foldback（收束式分支）**：只在 3~5 个关键剧情节点做真分支（辞职/卖站/放弃），
   其余分支很快收束回主干。玩家高估分支数量，这是叙事游戏的合法魔法。
4. **结局 = 状态评价函数，不是树的叶子**：结算时用一组规则对最终状态打分匹配
   （`收入>X 且 心态<Y → "赢了钱输了自己"`）。结局的"开放感"来自组合空间，
   新增结局零边际成本——这就是低成本实现"开放性结局"的正解。

### 3.3 可重玩性：借鉴 Roguelike 的元进度（Meta-progression）

单局随机（抽卡 + 角色种子）保证过程不重样；**局间解锁**保证长期动力：

- 达成特定结局 → 解锁新角色 / 新事件包 / 新开局条件（杀戮尖塔模式）；
- **事件图鉴 + 结局图鉴**：收集欲直接驱动重开（"还有 3 个隐藏结局没见过"），
  同时图鉴完成度是天然的分享物料；
- 稀有事件（银翅膀/风口卡）的"错过提示"制造合理遗憾，遗憾驱动下一局。

### 3.4 情绪曲线：心路历程要「设计」而不是「随机」

- 采用**谷-峰交替**的节拍控制：调度器保证连续负面事件不超过 N 次（防挫败弃游），
  也保证顺风局必有一次大逆风（防无聊）。随机是表象，节拍是导演。
- 第一笔收入（$0.01）这类关键正反馈做**专属演出**，把情绪峰值钉在设计好的位置。
- 结局文案负责升华：即使数值上"失败"，叙事上也要给玩家一个能自洽、能晒的人生总结。

### 3.5 动机理论（自我决定论 SDT）对照检查

- **自主感**：选择必须真的改变人生（storylet 状态耦合保证）——不能是换汤不换药的假选项；
- **胜任感**：成就梯度（第一刀→$1→$10→$100→$1000）+ 流派成型的"我会玩了"时刻；
- **归属感**：排行榜、图鉴晒图、社区投稿事件——玩家和出海圈子的互认。

### 3.6 远期差异化选项：LLM 动态事件（谨慎，二期后再议）

2026 年的技术条件下，可以让 LLM 在**固定机制模板内**生成事件文案变体（数值后果仍由规则控制），
解决内容消耗问题，并做出"每个人的人生真的不一样"的卖点。
风险：文案质量方差、服务器成本、失去"作者性"。建议：MVP 纯手写；
验证成功后先用 LLM 做**离线辅助生产**（人审后入库），在线动态生成最后再说。

## 4. 修订后的路线图

| 阶段 | 内容 | 验证什么 |
|---|---|---|
| 一期（MVP，2~3 周） | 人生引擎 v0 + 《出海建站》包（1 角色、~100 storylet、8 结局、结局卡） | 有人玩完并分享（玩完率>40%，分享率>15%） |
| 二期 | 补 4 角色 + 图鉴/解锁元进度 + 排行榜 | 重开率、7 日回访 |
| 三期 | 第二个人生包（候选：摆摊人生/考公人生——选社区呼声最高的）+ 投稿工具 | 引擎复用成本、UGC 意愿 |
| 远期 | 人生包平台化、LLM 辅助内容管线、联名人生包 | 平台叙事是否成立 |

**关键纪律**：一期只做《出海建站》，但引擎代码里不许出现任何"建站"字样的硬编码——
所有领域概念（收入、外链、AdSense）都在 JSON 里。这是用最小代价为"人生平台"留门。

## 5. 风险更新（相对第一份文档的增量）

1. **平台愿景导致 MVP 膨胀**：最大的新风险。对策：上表的"关键纪律"，引擎通用化以数据驱动为限，不做编辑器、不做 DSL、不做插件系统。
2. **B 类游戏的天花板**：事件驱动人生模拟的留存天生偏短（玩穿即弃），靠人生包更新续命——本质是内容订阅生意，管线效率决定生死。
3. **《模拟人生》式期待管理**：对外宣传不要碰"模拟人生"四个字，避免玩家带着沙盒预期进来失望；用"人生重开模拟器 × 大富翁"类比更准确。
