# 产品需求文档（PRD）— 儿童AI创作助手

版本：v0.1（MVP规划稿）
文档目的：作为 Claude Code 生成产品原型的开发依据

---

## 1. 产品概述

### 1.1 一句话定位
一个让孩子用说话就能"造出"网站或游戏的创作工具：孩子说出想法 → AI 理解并画出草图确认 → 孩子确认后自动生成可玩/可用的成品，并支持持续迭代。

### 1.2 目标用户
- 主用户：4–10 岁儿童，分两档设计交互复杂度
  - **低龄档（4–6岁）**：不识字，纯语音 + 图形化选择，禁止出现需要阅读的文字交互
  - **高龄档（7–10岁）**：可识字，允许简单文字确认作为语音的辅助
- 次用户（旁路角色）：家长，可查看生成记录和内容安全日志，但不参与孩子的创作主导过程

### 1.3 核心差异化
| 对比对象 | 它们的局限 | 本产品的差异 |
|---|---|---|
| AI聊天陪伴类产品 | 只产出对话，没有留存作品 | 每次创作都留下一个真实可玩/可用的成品 |
| 少儿编程工具（Scratch类） | 孩子要先学会工具语法 | 孩子零学习成本，工具主动翻译自然语言 |
| AI绘画/生成类工具 | 单次生成，无记忆、不可迭代 | 有作品档案，支持"接着上次的改" |

产品的核心壁垒不是模型能力，而是**"翻译层"**——把孩子语无伦次的描述可靠地转成可执行需求，并且每一步都用孩子能懂的方式确认。

### 1.4 设计北极星

**核心宗旨：释放孩子的想象力，让想象力成为现实——交互要更简单，呈现要更直观。**

这句话是所有交互设计的检验标准，而不是一条附加原则。每一个新增的步骤、确认、提问，都要先问自己：**这一步是在帮孩子把想象力变成现实，还是在拖慢这个过程？** 由此推出四条具体准则，贯穿全文：

1. **零提问优先**：遇到歧义，第一反应是"同时画出两个版本给孩子看"，而不是"先问后画"。语言提问是最后的兜底手段，不是常规路径。
2. **速度感即体验**：从"说出来"到"看见它"的间隔，是孩子感知"魔法发生"的核心时刻，草图生成必须是全流程响应最快的一环，宁可牺牲精细度。
3. **拆解过程对孩子完全隐形**：槽位、类型识别这些结构化拆解只是AI内部的骨架，孩子任何时候都不该感觉到自己在"被填表"或"被分析"。
4. **确认关卡只保留一道显式的**：技术上仍需要草稿和终稿两次质量检查，但孩子体感上只应该有一次"我要说个准话"的时刻，其余检查都以不打断创作节奏的方式隐式完成（见 3.4、3.5）。

## 2. 核心用户旅程（6阶段闭环）

```
① 语音倾听 → ② 需求拆解＋草图隐式确认 →（孩子主动打断→分歧处理，回到②）
→ ③ 复述确认＋终稿视觉【唯一显式确认关卡】 →（不满意→回到②）
→ ④ 深度构建 → ⑤ 成品完成＋继续迭代（→回到①）
```

设计原则：
- **展示优先于提问**：能画草图验证的，不用问句验证；歧义优先用"并排展示两个版本"解决，而不是提问
- **草稿阶段是隐式确认**：草图边生成边像讲故事一样呈现，孩子沉默即视为通过，只有主动打断才触发调整——错误拦截的功能保留，但不占用孩子的"决策感"
- **全流程只有一次显式确认**：唯一需要孩子明确表态"对/不对"的时刻是终稿视觉环节（③），因为那是真正开始耗费构建资源前的最后一道闸门
- **永远不说"不行"**：孩子提出无法直接实现的需求时，必须转译成一个可实现的相近版本，而不是拒绝

## 3. 核心功能模块

### 3.1 语音交互模块
- 语音转文字（STT）：需针对儿童语音（口齿不清、语速不稳、方言词汇）做识别优化
- 文字转语音（TTS）：语气活泼、语速偏慢、支持打断重说
- 低龄档全程语音驱动，不依赖屏幕阅读

### 3.2 需求拆解引擎（核心模块）

**固定维度槽位 schema**：

| 槽位 | 说明 | 示例 |
|---|---|---|
| subject（主体） | 谁/什么是主角 | 恐龙、公主、赛车 |
| scene（场景） | 发生在哪里 | 森林、太空、学校 |
| mechanic（核心玩法/功能） | 游戏怎么玩 / 网站做什么用 | 赛跑、收集金币、展示相册 |
| tone（情绪基调） | 决定色彩与音效风格 | 可爱、酷炫、神秘、搞笑 |
| key_detail（关键细节） | 孩子反复强调的执念点，优先级最高 | "一定要会喷火" |

**处理流程**：
1. 语音转文字
2. 识别作品类型（游戏 / 网站 / 故事 / 其他）
3. 用类型对应的槽位模板尝试填充五个槽位
4. 判断槽位是否"关键缺失或矛盾"：
   - 判定标准：**该槽位不同取值，是否会让最终草图明显不同？**
   - 是，且两种取值都能可视化区分 → **优先并排生成两个版本的草图**，让孩子直接指一个，而不是先问文字问题（进入 3.3 模块）
   - 是，但取值本身难以用图区分（比如抽象的规则类分歧）→ 才退化为一道选择题，作为兜底手段
   - 否 → 直接填入合理默认值，不打断孩子
5. 输出：结构化槽位 JSON ＋ 用于草图生成的 prompt

> 重要：这套槽位拆解只是给 AI 用的内部骨架。任何面向孩子的呈现（语音、画面、选项）都不能暴露"槽位""填充""识别类型"这类结构化痕迹，孩子看到的应该只是一张图、一句话、一个选择，而不是一次分析过程。

### 3.3 分歧处理模块（澄清追问）
- 触发条件：仅当某个槽位是"关键缺失或矛盾"时触发
- **默认路径（零提问优先）**：并排生成两个版本的低保真草图，孩子直接语音说"这个"或用手指/点击选择，全程不出现文字问句
- **兜底路径**：仅当分歧无法用图像区分时，才生成一道封闭式选择题（2–4个选项的图文卡片，低龄档配图不配字，高龄档可配短文字）
- 一次交互只处理一个分歧点，选完立即回到需求拆解，重新生成草图

### 3.4 可视化草图隐式确认模块
- 调用图片生成能力，基于槽位 JSON **以最快响应速度**生成一版低保真概念图（不追求精细，追求"方向对不对"，生成延迟是全流程重点优化对象）
- 呈现方式是"隐式确认"：语音以讲故事的口吻同步描述画面（例如"好嘞，恐龙们准备好在草地上冲刺啦——"），**不主动发起"对不对？"式提问**
- 孩子沉默或给出积极反应 → 默认视为通过，自动进入下一阶段
- 孩子主动打断说"不是这样的" → 触发分歧处理（3.3），修正后重新生成草图
- 这一环节不对孩子构成"决策负担"，只是错误拦截的隐性安全网

### 3.5 复述确认＋终稿视觉模块【全流程唯一显式确认关卡】
- 用孩子原话的关键词，语音复述一遍完整需求（"我们要做一个会喷火的恐龙赛跑游戏，对不对？"）
- 同时生成一版更完整的终稿效果图/关卡草图
- 这是全流程中唯一需要孩子明确说"对"才能继续的时刻，因为下一步就要开始真正耗费构建资源
- 孩子确认后才允许进入深度构建，避免资源浪费在方向错误的构建上

### 3.6 深度构建模块
- 按识别的作品类型分流：
  - 网站类：生成静态网页（HTML/CSS，可含简单交互）
  - 游戏类：生成基于模板的小游戏（Canvas/简单规则引擎）
- 构建过程用故事化进度呈现（如"正在给恐龙装上跑鞋…"），而非通用加载条

### 3.7 作品迭代与档案模块
- 每个孩子的每个作品持久化存储：槽位 JSON、对话历史、生成产物
- 完成后追问"还想加点什么？"，回答后重新进入①，形成延续性创作而非一次性生成

## 4. 交互设计要求

- 语音为主，屏幕呈现可视化内容作为语音的补充，而非依赖屏幕阅读
- 低龄档 UI：大按钮、强对比色、无文字依赖
- 高龄档 UI：可加简单文字标签，辅助确认
- 分歧处理优先用双版本图像并排呈现，只有无法可视化区分时才降级为封闭式选择，且不出现开放式输入框
- 草图生成速度是体验优先级最高的性能指标，需明显快于终稿生成
- 全流程只在终稿视觉环节设置一次显式确认，其余检查点均以不打断创作节奏的方式隐式完成
- "不行"类需求处理规则：AI 需先输出一句转译版本，再确认，而不是直接拒绝

---

## 5. 安全与家长层（非功能性要求）

- 内容安全过滤：拦截不适宜儿童的生成内容（图片、文本、构建产物均需过滤）
- 家长可查看生成记录与安全日志，但不能干预孩子创作过程中的实时交互
- 儿童数据隐私保护：语音、对话记录需明确的最小化存储与访问控制策略

## 6. 技术架构建议（供 Claude Code 参考）

| 层 | 建议方案 |
|---|---|
| 前端交互 | Web Speech API 或第三方儿童优化 STT/TTS；React 构建界面 |
| 需求拆解 | Claude API，要求以结构化 JSON 输出槽位（system prompt 固定 schema） |
| 草图/终稿生成 | 图片生成 API，传入槽位拼装的 prompt |
| 深度构建-网站 | 模板化网页生成（HTML/CSS/简单JS），Claude 生成代码 |
| 深度构建-游戏 | 基于预设小游戏模板（如 Canvas 简单规则引擎），Claude 填充参数与素材描述 |
| 数据存储 | 每个孩子的作品档案：槽位 JSON + 对话历史 + 生成产物路径 |

**槽位 JSON 示例**：
```json
{
  "creation_type": "game",
  "subject": "恐龙（多只）",
  "scene": "运动场/草地",
  "mechanic": "赛跑",
  "tone": "热闹、卡通风",
  "key_detail": "恐龙会喷火",
  "confidence": {
    "subject": "high",
    "scene": "medium_inferred",
    "mechanic": "resolved_by_clarify",
    "tone": "default",
    "key_detail": "high"
  }
}
```

## 7. MVP 范围建议

**MVP（v1，供 Claude Code 优先实现）**：
- Web 端原型，文字输入模拟语音（暂不接入真实 STT/TTS）
- 仅支持"游戏"一种作品类型
- 完整跑通 6 阶段闭环：拆解 → 草图确认 → 分歧处理 → 复述确认 → 深度构建（简单网页小游戏）→ 完成
- 槽位判定与默认填充逻辑需真实生效，而非写死流程

**V2**：接入真实语音交互、新增"网站"类型、加入低龄档/高龄档 UI 分层

**V3**：家长层、作品持久化档案、多轮迭代体验、内容安全过滤上线

---

## 8. 成功指标

- 从①到④的完成转化率
- 平均澄清轮次（目标 ≤2 次/作品，且其中显式选择题占比应远低于双版本图像选择）
- 草图生成响应时长（核心体验指标，目标持续压缩）
- 草稿阶段隐式确认通过率（孩子未主动打断即通过的比例，越高说明拆解越准）
- 孩子对成品的"这就是我想要的"确认率
- 复访 / 继续迭代率

---

## 9. 开放问题（需在开发中进一步决策）

- 游戏类型深度构建的技术选型（自研简易引擎 vs 现成模板库）
- 儿童语音识别的方言/口齿不清适配方案
- 分歧处理选项的生成质量如何保证"选项本身也是孩子能听懂的"
